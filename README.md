# Fp. HwNN

## Установка

Нужны компилятор GHC 9.10.3, система сборки cabal, линтер hlint и `make`.
Компилятор и cabal ставятся через [ghcup](https://www.haskell.org/ghcup/) одной командой.

Linux и macOS:

```sh
curl --proto '=https' --tlsv1.2 -sSf https://get-ghcup.haskell.org | sh
```

Windows (PowerShell, команда с сайта ghcup):

```powershell
Set-ExecutionPolicy Bypass -Scope Process -Force;[System.Net.ServicePointManager]::SecurityProtocol = [System.Net.ServicePointManager]::SecurityProtocol -bor 3072; try { & ([ScriptBlock]::Create((Invoke-WebRequest https://www.haskell.org/ghcup/sh/bootstrap-haskell.ps1 -UseBasicParsing))) -Interactive -DisableCurl } catch { Write-Error $_ }
```

Установщик задаст вопросы: соглашайтесь поставить GHC и cabal, HLS (Haskell Language Server) — по желанию, он даёт подсказки в редакторе.
После установки выберите нужную версию компилятора: `ghcup install ghc 9.10.3 && ghcup set ghc 9.10.3`.
Версия зафиксирована в `cabal.project`, поэтому другой компилятор сборка не примет.

Линтер подсказывает, как упростить код. На статус задач его подсказки не влияют, но `make check` показывает их каждый раз, а ревью на них смотрит.
Быстрее всего взять готовый бинарник из [релизов hlint](https://github.com/ndmitchell/hlint/releases) (есть для Linux, macOS и Windows) и положить его в `PATH`; пакетный менеджер вашей системы тоже подойдёт. `cabal install hlint` работает, но собирает линтер из исходников долго.
Если hlint выдаёт ошибки на выданный вам код, обновите его (нужна версия не ниже 3.4.1).

Все команды домашки собраны в `Makefile`, `make` без аргументов печатает их список. На Linux и macOS `make` уже есть или ставится пакетным менеджером; на Windows он есть в оболочке MSYS2, которую устанавливает ghcup (`pacman -S make`).

## Порядок работы

1. Клонируйте свой репозиторий: `git clone git@github.com:...`
2. Соберите проект: `make build`. Первый раз это долго, потому что собираются все зависимости.
3. Выполняйте задания в `src/`.
4. Загружайте код в интерпретатор: `cabal repl`
    * После правок перезагружайте интерпретатор командой `:r` — так вы сразу видите ошибки типов.
    * Проверяйте решения вручную, импортировав нужный модуль: `import BlockN`.
5. Записывайте номера решённых заданий в `solved-tasks.txt`, например `1.1 1.2` (первые два задания первого блока).
6. Запускайте `make check`: линтер и тесты для перечисленных заданий. Перед сдачей избавьтесь от всех ошибок тестов.
7. Тесты отдельных заданий: `make check ONLY="1.1 1.2"`.

Строгого стиля кодирования нет, ориентируйтесь на код тестов в `test/`.

## Домашки по λ-исчислению

В первые недели в `src/` лежит не Haskell, а файл `src/hw.lam` с заданиями; определения с лекции и практики — в `src/prelude.lam`. Ни строчки Haskell писать не нужно: он здесь только собирает проверялку, и та же проверялка запускается в CI.

1. Решайте задания в `src/hw.lam`: на месте каждой дырки `...` пишется ответ, условия — в комментариях перед задачей.
2. Играйте с термами в интерпретаторе: `cabal run lambda -- load src/hw.lam`. Терм сам по себе редуцируется до нормальной формы (`mult 2 3`), `:follow` показывает каждый шаг, `:step` один шаг, `:explain` дерево терма, `:decode` печатает результат как число, пару или список, `:type` наиболее общий тип, `:help` всё остальное.
3. Дальше как обычно: `solved-tasks.txt`, `make check`, отчёт по всему файлу без раннера `cabal run lambda -- check src/hw.lam`.

Как пишутся термы:

```
name = \x y. body        -- определение; \x y. — то же, что \x. \y.; можно писать λ или ->
f x y                    -- аппликация, скобки только для группировки: f x y это (f x) y
3                        -- число Чёрча ⌜3⌝ = \s z. s (s (s z))
...                      -- дырка: сюда пишется ответ
-- текст                 -- комментарий
```

Имена — буквы, цифры, `_` и штрих: `K'` в прелюдии — это K* с лекции. Свободные переменные можно использовать только те, что перечислены в строке `vars` в начале файла; любое другое незнакомое имя проверялка считает опечаткой.

Проверки в файле — открытые тесты, их можно и нужно читать: `expect левое = правое` вычисляет обе стороны и сравнивает их (с точностью до α и η); `chain name = ...` — цепочка редукций по шагу на строку (`~b~>` один β-шаг, `~d~>` раскрыто или свёрнуто одно имя, `=a=` переименование связанной переменной, `~s~>` выполнена подстановка, `~~>` до трёх шагов сразу), и если проверялка не согласна с переходом, она скажет, между какими строками и какие шаги были возможны; `free`, `rename`, `minimal`, `check`, `type`, `church`, `inhabit`, `family` объяснены в условиях тех задач, где встречаются. Полное описание формата — в `meta-utils/lambda/FORMAT.md`.

## Уровни задач

Список задач и их уровни лежат в файле `TASKS` в корне репозитория. Уровня три:

* уровень 1 — обязательные задачи: домашка сдана, когда все они в статусе DONE;
* уровень 2 — задачи, к которым стоит вернуться до сессии;
* уровень 3 — челлендж для тех, кому мало.

Некоторые задачи взаимозаменяемы: правило `rule any k of: ...` в `TASKS` означает, что из перечисленных достаточно закрыть любые k.

У каждой задачи после прогона тестов три возможных статуса: DONE (все тесты прошли), PARTIAL (часть прошла), FAILED (ничего не прошло). Задачи, не перечисленные в `solved-tasks.txt`, получают статус TODO. Баллов за задачи нет: важно только, закрыт ли уровень 1.

## Сдача

Сдача — это пуш в ветку `main` вашего репозитория. Pull request `main → feedback` открывается автоматически после первого пуша, в нём после каждого прогона CI появляется отчёт со статусами задач и вердиктом по уровню 1. Ничего никуда отправлять не нужно.

Если вашего репозитория в организации нет, создайте его сами: откройте шаблон домашки, нажмите *Use this template*, владелец `fpcourse-students`, имя `<шаблон>-<ваш логин GitHub>`, публичный. Первый пуш заведёт всё остальное.

Перед сдачей занесите сдаваемые задания в `solved-tasks.txt`:

* `make submit` — сдать версию: сначала локальная проверка, затем коммит с префиксом `submit:`, который говорит, что эту версию стоит посмотреть ревью. Сдавать можно сколько угодно раз до дедлайна;
* `make tmp` — временный пуш без прогона CI, чтобы не тратить его время.

Дедлайн у домашки один. Итерации ожидаемы: сдали, получили отчёт и ревью, поправили, сдали снова.

Ревью:

* LLM-ревью появляется в PR на сданных версиях, пару раз в неделю, не больше трёх раз на домашку. Его замечания — советы, статус задач они не меняют;
* после дедлайна начинается открытое peer-ревью в PR: читайте чужой код и отвечайте на комментарии к своему.

По желанию — `explain.md`: короткие объяснения своих решений, см. заготовку в файле.

## Оценивание решений

Языки различаются по выразительности.
Чем выразительнее язык, тем проще и лаконичнее можно на нем выражать свои мысли.
И тем проще писать очень плохой код.
Современные языки двигаются в сторону выразительности, а Haskell уже там.
Таким образом, важно стараться писать хороший читаемый код на Haskell, потому что очень плохой код написать на нём слишком просто.

Если код трудно читать, и если трудно убедиться глазами в его корректности, вы получите замечания в ревью.
Старайтесь смотреть со стороны на свои решения, выбирать подходящие уровни абстракции и конструировать нужное количество промежуточных слоёв, которые делают решение понятным в каждом приближении.
Совсем безалаберное форматирование тоже будет отмечено в ревью.

Поскольку мы на этом курсе живём в парадигме переизобретания программирования, для нас почти ничего не должно быть магией.
Когда вы используете тот или иной механизм, будьте готовы объяснить, как он работает.
Использование всегда только самых базовых вещей - не вариант, выбор неправильного уровня абстракции тоже предмет ревью.

Качество кода — предмет ревью и разговора у доски, а не баллов.

## Помощь

Не стесняйтесь обращаться за помощью к вашим преподавателям, они тут как раз для этого.
Все контакты вы найдёте на вики.
Нам не сложно и в радость вам помогать, а наблюдать молчаливое непонимание как раз грустно.
Не обесценивайте свои трудности, ищите поддержки - и найдёте.

Также просите помощи у своих одногруппников, помогать интересно и полезно.

Если вы помогаете, не навредите!
Предлагайте объяснения, а не ответы.
Отталкивайтесь от потребностей собеседника, а не от желания показать себя.
Человеку и так может быть не очень здорово, очень просто закопать его ещё глубже, говоря избыток умных слов и демонстрируя свою эрудицию.

Помните: у всех разная подготовка и способности к построению определённых видов умозрительных конструкций, с этим особо ничего не сделаешь.
Но это никак вас не определяет.
Чем сложнее даётся, тем ценнее любой шажок.
Не будьте слишком требовательны к себе и двигайтесь в своём темпе.
Всё будет хорошо, гарантируем.

Не всем просто психологически обращаться за помощью.
Но это важно, без этого никак.
Попробуйте относиться к этому как к части работы и постарайтесь, оно окупится.
